# Security controls and current evidence

This page records deployment and multiplayer guardrails for the authored browser game and relay. It describes defense in depth; it is not a security audit or a guarantee against denial of service.

## Multiplayer admission and resource bounds

Production room creation and connection use Cloudflare native rate-limit bindings configured for 12 creates per IP per minute and 120 connections per IP per minute. Cloudflare documents these counters as permissive and eventually consistent: updates are asynchronous, and counters are local to each Cloudflare location, so they are not a strict global cutoff or accurate accounting system ([Cloudflare Rate Limiting API documentation](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)). Requests are rejected when the client IP, required binding, or serialized Durable Object admission service is unavailable. Streaming request bodies are capped at 512 bytes. The admission object enforces global leased-room and creation budgets (256 rooms, 120 creates/minute, 2,000 creates/day, 2,000 connections/minute, and 100,000 connections/day). Reservations roll back when room creation fails. Rapid host bursts produced variable 201/409 responses without a reliable immediate cutoff, as expected from the binding's asynchronous counters. A paced public run sent 14 requests at 1.2-second intervals and observed `[201, twelve 409 responses, 429]`, allocating one room. The exact global serialized budgets are the hard application-level ceilings.

Each room has a unique 128-bit instance identity. Retiring a room releases its quota lease. A 30-second cleanup alarm clears retired room storage while serialized with requests through `blockConcurrencyWhile`. A real Wrangler Worker/Rust Durable Object check confirmed a closed room returns 410 immediately, 404 after 35 seconds, and permits reuse of its code with a different owner capability. Cleanup checks the room identity again after admission awaits, so a delayed cleanup cannot erase a newly reused room. Create requests parse their body before ownership checks to avoid concurrent code reuse, and cleanup alarms retry when admission is unavailable. A legacy closed-room record schedules cleanup when touched; unvisited old closed records are not globally swept. These budgets constrain application-level resource use but do not replace Cloudflare edge protections or establish a maximum-cost guarantee under all traffic patterns.

Room-race packets (`research/MULTIPLAYER.md` "Room races") reuse these bounds: race `GameState` is relayed only from the host of a started private room, `Progress` only from a rostered rider on the room's map with its peer id stamped by the relay; both are bounded by the codec (laps, slots, finite distance, times ≤ 2 h) and fall under the per-connection message and byte budget. Room-race CPU motion (`Cpus`, kind 16) is forwarded only from the host of a started private room on the room's map to race-aware riders, at most four CPUs per message with every pose validated as a rider snapshot. Race results are host-authoritative over self-reported progress, so a modified client can misreport its own finish; online races save no profile progress or records.

## Deployment and browser controls

The production Worker serves a Content Security Policy and security headers configured for the authored application, WebAssembly and multiplayer WebSockets. The local multiplayer test proxy binds to loopback by default. CI scans the working tree and broader Git history for secrets with redacted findings. `CODEOWNERS` routes review to the repository owner, but does not enforce approval until branch protection is available. Workflow checks and the production environment restrict deployment to the owner and `main`.

The GitHub production environment is API-verified to restrict deployments to `main`. The deployed production run also verified live `LobbyAdmission`, required-guard, and native rate-limit bindings with the configured thresholds above. GitHub rejected the branch-protection API request with HTTP 403 because private-repository branch protection requires a higher plan (or a public repository). The repository remains private; branch protection is therefore still pending and is not claimed as enforced. Existing Cloudflare credentials were refreshed without adding scopes. Live Cloudflare observability settings were verified with query-string redaction enabled and invocation logs disabled. The native Chrome token policy was verified to have Account Settings Read and Individual Workers Editor access limited to `atv-offroad-fury-2`; no credential value was accessed, and no rotation was needed.

The host checkpoint passed `make check` (workspace formatting, Rust tests and Clippy, and 95 frontend tests), `make verify`, WebAssembly and Rust relay builds, 19 security/Worker JavaScript tests, 7 relay Rust tests, 2 secret-scanner tests, and 35 release checks (one intentional skip). Commit `3928e38bf9d6d61ddc55e532b37c07f9645ebb0d` passed GitHub CI and production deployment run `38469544837`; both public domains serve that commit. Public frontend checks, all 16 public relay checks, and the copied-invite browser run passed: each client rendered 13 remote draws, observed 4.924 feet of movement, distinct quad/rider models, audio, host-exit cleanup, and no page errors. The R2 upload reported 453 objects, one changed object. Full verification passed for both the Workers and custom domains, each with 452 served objects, 42 static files, 176 log entries and 137 screenshots. Public checks also confirmed expected responses for security headers, private paths (404), foreign origins (403), and a 513-byte body (413). The paced public rate-limit proof is described above. These checks verify this release path, not geographic load or physical-phone behavior.

The security scanner reduces accidental secret exposure in repository history; it does not inspect external services or guarantee that a secret was never used. Rate budgets and cleanup reduce abuse and stale-room accumulation but are not a complete DDoS defense. The unconfigured branch-protection rule remains a governance gap.

## Cloud saves

The Pass Key save API (`/api/save`, `/api/share`) is described in `research/CLOUD_SAVE.md`. It stores only SHA-256 hashes of keys and share codes in D1, never IPs or raw codes; it refuses foreign, opaque (`null`) and cross-site browser origins while accepting native clients that send no `Origin`; it streams bodies with a 66 KiB cap and a 64 KiB save cap; and it uses four native per-IP rate-limit bindings (writes are also limited per key hash). Missing storage, limiter bindings or client IP fail closed with 503. A Pass Key is a bearer code by design: anyone holding it can overwrite that save, mitigated by the last 10 revisions and the restore endpoint. There is no global storage ceiling yet.
